# 实验计划：GitHub Actions 网络出口

## 目标

验证托管 Runner 的出站网络特征与 Job 生命周期，并明确区分“Runner 自己访问互联网”和“本地设备经由 Runner 转发流量”。

## E1：Runner 出口 IP

**操作**：手动运行 `Freeman: Runner egress probe`，`hold_seconds=0`。

**记录**：
- Workflow run URL、时间、Runner OS/架构；
- ipify、AWS checkip、ifconfig.me 三个服务的响应；
- 三个服务是否返回相同的 IP 字符串。

**通过标准**：至少一个服务成功返回可解析的公网 IP 字符串。若不同服务结果不同，先重复实验并记录差异，不直接推断原因。

## E2：Job 生命周期

**操作**：分别以 `hold_seconds=0`、`60`、`300` 运行。不要将短等待实验扩展成长期常驻任务。

**通过标准**：日志显示等待前后时间戳；实际耗时与请求等待时间大致一致（允许 Runner 启动和调度开销）。Job 的 `timeout-minutes: 15` 是安全上限，不是可用时长承诺。

## E3：本地请求是否经过 Runner

E1/E2 **不能**证明本地流量已经经过 Runner。E3 必须由本地设备发起请求，并通过受认证的私有连接到达远端实验端点，然后在远端记录目标请求的出口 IP。

本仓库当前不创建公开、无认证的通用代理，也不尝试将 GitHub 托管 Runner 变成长期个人代理服务。若确有必要继续 E3，先评估 GitHub Actions 的适用政策与安全边界；更稳妥的技术验证环境是自己控制的临时 VPS，或在你管理的主机上运行自托管 Runner。不要将代理密码、访问令牌或私钥写入仓库、日志或工件。

## 当前范围

- 已实现：手动触发的出口 IP 探测；0–600 秒的短等待；15 分钟 Job 超时；最小只读仓库权限。
- 未实现：本地设备到 Runner 的入站通道、通用 HTTP/SOCKS 代理、全局流量接管。
